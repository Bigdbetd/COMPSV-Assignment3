The undo/redo manager needs to retrieve the most recent action first. A stack provides that last-in, first-out order: each new action goes on top of the undo stack, and Undo removes that top action and places it on the redo stack. Redo reverses that transfer, so repeated undo and redo operations follow the correct sequence. Performing a new action replaces the redo stack because the old undone actions no longer belong to the current sequence of edits. The program stores descriptions of actions as a simulation; a real editor would also store enough information to reverse and reapply the actual changes.

The help desk has the opposite ordering requirement. The first customer to arrive should be the first helped, so a first-in, first-out queue is appropriate. Enqueue adds a ticket at the rear, while dequeue and peek work at the front. Maintaining both front and rear pointers lets those operations run in constant time, even as the line grows. When the last customer is removed, both pointers become None so the next arrival starts a fresh queue correctly.

Both structures use linked Node objects rather than Python lists. A Node holds one value and a link to the next node. The stack only tracks its top; the queue tracks both ends. Unlike a list, these classes expose only operations consistent with their intended access order, preventing callers from inserting or removing an item in the middle. Python lists already make effective stacks using append and pop, but removing the first list element shifts the remaining elements. This linked queue removes the front node without shifting any elements.
